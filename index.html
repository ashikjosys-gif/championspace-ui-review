Product experience review · 11 October 2026

Two spaces. A clearer path through both.

ChampionSpace and TournamentSpace already have substantial working functionality. The next release should make that functionality easier to find, understand and use—starting with mobile layouts, trustworthy status information and a clear next action.

VerdictWhat existsImprovementsGraphics & slideshowsRelease planCoverage
Recommendation

Stabilize and simplify before expanding.

ChampionSpace: the breadth of the product is ahead of its navigation clarity. Athlete history, assessments, coaching and parent reports are already connected conceptually, but competing dashboards, mixed metrics and mobile defects interrupt the experience.

TournamentSpace: the core match-day workflow is tangible and usable. Scoring is the strongest part. Organizer setup and spectator discovery need a clearer sequence, and stale event data needs honest labels.

First release priorities: repair mobile Passport/report layouts; correct summary charts; fix stale tournament timing; restore local PDF generation; clarify academy context and entry into each space.
Preserve: the red/graphite visual identity, role-specific summaries, the existing assessment stepper, report audience lenses, bracket/grid views, import previews and large referee scoring controls.

This is an expert interface review and sampled workflow verification. It is not a completed user usability study or a claim that every save, permission boundary and recovery path has passed.

Prioritized findings

What needs to improve.

P1 = fix before broader rollout of the affected flow. P2 = usability, clarity or trust improvement. S/M/L are relative effort bands, not delivery estimates. The local-only PDF issue must be checked against the intended deployment.

P1 ChampionSpace · effort M · F01

Repair the Passport and report on phones

At 390px, the Passport title wraps almost one letter per line. The report cover also squeezes its title into a very narrow column; its academy name and date run together. This obstructs the main content.

Improve: Use a single-column mobile header and cover; move metadata and actions below the title. Check long names at 320, 390, 768 and 1440px and at 200% zoom.

P1 ChampionSpace · effort M · F02

Replace misleading percentage bars

Team & access presents 5 total and 5 active as 50% each. A group shows 7 athletes, capacity 8 and 1 open spot as 44%, 50%, 6%. These are overlapping values, not parts of a whole. Report bars retain a visible red segment for zero priorities.

Improve: Use plain counts for different units. Show group occupancy as 7 of 8 (87.5%). Restrict stacked percentages to mutually exclusive categories in the same population; render zero as zero. Audit the shared pulse component everywhere.

Make event and match timing truthful

The deployed event is dated 26 September 2026, but on 11 October an upcoming match still reads “Starting now.” A paused match and a live fun event remain visible without an indication of how old their state is.

Improve: Derive labels from the full scheduled date, event lifecycle and last update. Distinguish upcoming, delayed, live, paused, completed and archived; show a last-updated time and event date.

  2. Parent: understand a child’s progress, interpret a benchmark caveat and identify the next step.
  3. Organizer: enter players, review the draw, resolve scheduling gaps and prepare referee access.
  4. Referee: start a match, score, undo, pause/resume and finish without losing state.
  5. Spectator: find a player, identify the next match and distinguish live from historical results.
Evidence and limits

What was actually checked.

ChampionSpace: the running local Flutter application at port 5252, using the existing local API and seeded/demo accounts. Seven roles were sampled. Desktop captures use 1440px; phone captures use 390px. Read-only navigation, forms, reports, error states and sample detail records were examined. Existing real academy records were not edited.

TournamentSpace: deployed spectator pages at championspace-tournament.onrender.com were read only. Administrator and referee workflows were tested in a separate temporary SQLite database at port 8194, using the existing built frontend and current source API. This does not establish exact frontend version parity with the deployment.

Passed isolated workflow: add four synthetic players → generate two semifinals and a final → start a match → score both sides → undo → pause → sign in as the court referee → resume → complete 21–1, 21–0 → verify the result and winner in the final. The completed result also appeared in the local live display. All eight tournament sections were captured at phone width without document-level horizontal overflow.

Public website: all 27 routes at local port 5177 were captured at desktop and phone widths; no document-level horizontal overflow was detected. This is the current local website, not a verification of every public deployment or separate design proposal.

Still needs dedicated verification: invitation-token acceptance, an immutable saved-report route, a complete assessment save lifecycle, all athlete/academy edits, file-import edge cases, actual PDF export from every export control, walkovers, all fun-event submission modes, permission boundaries, reconnect/offline scoring, load behavior and accessibility with assistive technology. Automatic video analysis was unavailable in the reviewed runtime. No full WCAG or security certification is claimed.

Review baseline: source checkout shared-repo-sync, HEAD 43e1cf2d4b158216caba5ffac11260484aa6fb09 with pre-existing local edits. No application source changes were made for this review. The runtime build may differ from source; observed UI is the basis for the findings.
